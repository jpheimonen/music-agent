# Music

Local TypeScript music app with an AI DJ. The DJ picks music to your taste, plays it from YouTube, your own MP3s or live radio, and talks with you about what you like. The setup page and `/api/v1/capabilities` report unavailable features explicitly.

## Run

Requires Node.js 24 and npm 11. From the repository root:

```sh
npm ci
npm run build
npm start
```

Open http://127.0.0.1:8787. The server binds loopback only and serves the built frontend and API from one origin. For development, run `npm run dev`, then open http://127.0.0.1:5173; Vite proxies `/api` to the backend. `npm run typecheck` checks all workspaces.

The browser tab shows what is playing. The app can be installed from the browser as a standalone window. Its service worker in `apps/web/public/sw.js` caches only the page shell for offline start-up. API calls and audio always go to the server. After changing the shell, bump `CACHE` in that file.

Set environment values before starting. `.env.example` lists them without credentials. `MUSIC_LIBRARY_ROOT` must be absolute. `MUSIC_DATA_DIR` defaults to the repository's `data/` directory; relative `MUSIC_DATA_DIR` and `MUSIC_CODEX_HOME` overrides are resolved from the repository root even when npm starts the server in its workspace. `MUSIC_YTDLP_BIN`, if set, must be an absolute path to your own yt-dlp. Do not expose the data directory publicly. Optional station endpoint overrides must be credential-free HTTPS.

The browser uses `/api/v1`. JSON API errors include a stable code and request ID. No CORS is enabled. Requests are limited to local Host and same-origin mutation Origin. Jobs run in memory; cancellation is best effort, and a server restart does not resume them.

## Media setup

The app is led by the AI DJ. The DJ panel sits on the left and stays in view; the player is docked to the bottom of the window with what's playing, Play/Pause, Skip, Like, Not for me, the position and the volume. Media keys and the system's media controls work too.

Tell the DJ what you'd like to hear and select **Start the DJ**. It queues picks under **Up next** with a note on why it chose each one, and keeps going as tracks end. While it plays, talk to the DJ in the same box: ask for something calmer, tell it what you love or can't stand. It answers, saves what it learned as notes, and changes the music when you ask for different music. **Interview me about my taste** starts a short interview, one question at a time, with answers you can tap. **Your taste** lists the DJ's notes, and **Forget** deletes one.

The source buttons choose where the DJ picks from: **YouTube** or **Your collection**. Switching between them keeps the track that's playing and replaces only the DJ's upcoming picks. **Live radio** shows the stations without stopping anything; picking a station starts it, and the DJ keeps its queue until you press **Back to the DJ**.

In **Up next**, 👎 removes a song and records a dislike, while **Remove** only removes it. **Not for me** on the playing track records a dislike and skips. Both can be undone from the notice that appears. Skips and finished tracks also teach the DJ. You never paste YouTube links. Under **Your collection** you can also browse and play your own MP3s yourself. **Setup** shows what is ready and how to fix what isn't. The theme follows your system's light or dark setting; the header menu can pin Light or Dark.

Set `MUSIC_LIBRARY_ROOT` to an absolute readable MP3 directory before starting the server, then select **Rescan** under **Your collection**.

For API access, POST `/api/v1/library/scans` with `{}` to build the catalog; poll `/api/v1/jobs/:id`. Pass `{ "full": true }` to rehash every file. `GET /api/v1/library/tracks?q=&cursor=&limit=` returns bounded pages. Indexed files use full content SHA-256 identities and support GET/HEAD byte ranges at `/api/v1/media/local/:id`. The catalog under `MUSIC_DATA_DIR` is rebuildable. Changing tags changes identity.

YouTube plays as audio through [yt-dlp](https://github.com/yt-dlp/yt-dlp), not the YouTube IFrame, so videos that block embedding still play. No YouTube API key is needed. On first start the server downloads the latest official yt-dlp release into `MUSIC_DATA_DIR/tools/` and installs it only if it matches the release's SHA2-256SUMS. It checks for a yt-dlp update once a day, when no yt-dlp process is running, because old versions stop working when YouTube changes. The download needs Python 3.10 or newer as `python3`. To use your own copy instead, set `MUSIC_YTDLP_BIN`; the app never updates that copy. yt-dlp runs with the server's own Node as its JavaScript runtime. Setup shows the installed version.

`GET /api/v1/media/youtube/:videoId` streams a video's audio with HTTP range support. The server gets the stream URL with yt-dlp, caches it until shortly before YouTube expires it, and fetches a fresh one when YouTube refuses a request. Only `googlevideo.com` stream hosts are followed. In the browser, a connection that drops mid-track reloads at the same position. `POST /api/v1/youtube/search` runs a yt-dlp YouTube search as an asynchronous job; poll its `jobId` through `/api/v1/jobs/:id`. Direct video URL/ID resolution works at `POST /api/v1/youtube/resolve`; the app itself doesn't ask for links.

Live radio offers 22 stations: KEXP, BBC Radio 4, Yle Radio 1, Radio Helsinki, FIP, WFMU, NTS 1, NTS 2, Radio Paradise's Main Mix, Worldwide FM, dublab, Refuge Worldwide, Radio 80000, Cashmere Radio, Noods Radio, Resonance 104.4 FM, Radio Nova, Radio Meuh, Ö1, WWOZ, Intergalactic FM and Radio Swiss Jazz. The selection favours independent presenters, freeform discoveries, jazz, global music and cultural programming. Each stream was checked to play, and the stations added in October 2026 link their entry in the public radio-browser directory as provenance. Each preset describes its sound; the station panel links to its own site.

`GET /api/v1/stations` lists the configured stations; `POST /api/v1/stations/:id/resolve` selects a browser stream without a network health check. Stream provenance is included in the station descriptors. Availability means configured, not a live health guarantee. Optional overrides for the original three stations must be credential-free HTTPS.

`GET /api/v1/stations/:id/now-playing` returns `current`, `unavailable`, `stale` or `unsupported`. The app polls while listening and shows reported tracks from KEXP, FIP and Radio Paradise, programmes from NTS, and Radio Helsinki's current song or programme when its public HTML fields are accessible. Radio Helsinki's site can refuse automated access; missing fields or access errors show an unavailable message. Radio Meuh, Intergalactic FM and Radio Swiss Jazz name the track inside the audio stream (ICY metadata), and dublab, Refuge Worldwide, Radio 80000, Noods Radio and Resonance name the show. The server reads only up to the stream's first metadata block. Placeholder titles between shows count as unavailable. Yle Radio 1, BBC Radio 4, WFMU, Worldwide FM, Cashmere Radio, Radio Nova, Ö1 and WWOZ currently have no metadata adapter. Custom stream overrides disable metadata to avoid showing another broadcast's tracks.

Metadata requests use fixed public URLs, an eight-second deadline, a 512 KiB response limit and a 30-second cache with shared concurrent requests. Titles expire after at most 90 seconds without another successful observation, sooner when a feed provides a track or programme end. KEXP reports starts rather than ends, so its latest logged track is accepted for at most 15 minutes after its start. Old or future records are rejected; cached schedules with explicit intervals are accepted only during those intervals. HTTP cache age reduces relative track durations and the freshness of undated HTML. The browser clears expired information even during a slow refresh and discards requests from stopped or previous stations. A station's report can differ slightly from the buffered audio; metadata failures do not stop playback.

Current metadata includes `kind` (`track` or `programme`), `title`, nullable `artist` and `startedAt`, `checkedAt`, `expiresAt` and a station attribution `sourceUrl`. Other statuses omit the track fields. NTS programme names describe the show on air; they are not individual song titles.

## Taste data

`MUSIC_DATA_DIR` (default repository-root `data/`) contains the authoritative `likes.csv`, `dislikes.csv`, and `musical_taste.md`. Keep this directory private and back it up as a unit. The CSV files are UTF-8 RFC4180 with header `schema_version,media_id,source,title,artist,recorded_at`, schema version `1`, one row per media ID, and UTC ISO8601 timestamps. A media ID appears in at most one file. `musical_taste.md` has YAML-like front matter with `schema_version`, `summary_revision`, `based_on_feedback_revision`, and `generated_at`. Its body is derived narrative; the CSVs are the explicit feedback facts.

The server also writes `taste-manifest.json` (revisions, hashes, retry receipts), `taste-pending.json` during a commit, and `.taste.lock` while running. Only one server process may use the directory. Reactions are immediately durable and increment the feedback revision; summary synthesis has a separate revision and can lag. The internal `TasteRepository.commitSummary` operation rejects generated text based on stale feedback or summary revisions. Codex must never write these files directly.

`PUT /api/v1/feedback/:mediaId` accepts JSON `{ "reaction": "like" | "dislike" | "neutral", "expectedRevision": number, "media"?: MediaItem }` and requires an `Idempotency-Key` header of 8–128 letters, digits, `_`, or `-`. A retry with the same key and request returns the original canonical result. A different request under that key or a stale revision returns `revision_conflict`. `GET /api/v1/taste?mediaIds=id1,id2` returns current feedback and the summary's separate `current`, `pending`, or `failed` status. The `media` field supplies display metadata when a reaction is first recorded; without it the media ID is used as the CSV title. Songs heard on the radio can be liked too: when a station reports the current track, its now-playing response includes a `songId` of the form `radio:<sha256>`, derived from artist and title so the same song shares one ID across stations. Send that ID with `"radioSong": { "title", "artist" }` instead of `media`; the server returns 400 if they do not match, and stores the row with source `radio`.

`dj-memory.json` in the same directory holds what the DJ learned in conversation: up to 60 notes, the last 80 messages and the last 300 plays, each marked finished or skipped. The server writes it atomically. An unreadable file is renamed `dj-memory.invalid-<time>.json` and a new one is started. `GET /api/v1/dj/memory` returns the notes and conversation. `POST /api/v1/dj/messages` with `{ "text", "mode": "chat" | "interview", "djOn" }` starts a conversation job whose result has the DJ's message, an optional `steer` direction for the music and the updated memory. `DELETE /api/v1/dj/notes/:id` forgets a note, and `DELETE /api/v1/dj/conversation` clears the conversation but keeps the notes. `POST /api/v1/listening` with `{ "media", "outcome": "finished" | "skipped", "listenedSeconds", "durationSeconds" }` records a play.

On startup, a valid pending journal is replayed before requests are served. A crash may leave `.taste.lock`; startup removes it only when its recorded PID no longer exists. Valid offline edits are imported on restart with a new feedback revision and a `taste-last-known-good` backup. Stop the server before editing; changes made while it runs produce `external_file_change` on the next write. If startup reports malformed data, incomplete files, or a conflicting journal, preserve the directory and restore a known-good copy or repair the named file before restarting. The server does not overwrite malformed existing taste files. Do not delete a pending journal to force startup; it may contain the only complete commit after-image.

## Codex DJ setup

`npm ci` installs the pinned `codex-cli 0.156.1` alongside `@openai/codex-sdk` 0.156.1; an external pinned CLI on `PATH` or an absolute `MUSIC_CODEX_BIN` path also works. The server resolves the native runtime behind the npm CLI shim and checks its version. It uses your existing Codex login: `MUSIC_CODEX_HOME` if set, otherwise the server's `CODEX_HOME`, otherwise the OS user's `~/.codex`. Relative `MUSIC_CODEX_HOME` and `CODEX_HOME` values resolve from the repository root. No second app login is needed. If the app reports `setup_required`, check that the selected home is the one your normal Codex CLI session uses and that the CLI is logged in there, then restart the server.

The app does not read or copy authentication tokens, modify your `config.toml`, or run login/logout. It passes the real user home and selected Codex home to the trusted CLI for file or OS-keyring credentials. Each music job disables configured MCP servers, hooks, notifications, apps, plugins and shell tools for that invocation. A config that cannot be safely overlaid reports `codex_config_incompatible`; harmless personal settings remain valid. A ChatGPT account with Codex access, network connectivity, and available plan usage is required. Selected taste, notes, recent listening, conversation and media metadata are sent to the Codex inference service. The server excludes unrelated environment variables from the Codex child process.

At startup the server checks the CLI version, your existing login and the model catalog. If any of these fail, AI routes are disabled, while manual media and feedback still work.

Music jobs run Codex without its sandbox (`danger-full-access`), so the DJ also works on hosts where bubblewrap cannot start, such as Ubuntu 24.04 and later. This is a deliberate choice for a personal, locally run app: Codex can read and write anything your user account can. Shell, MCP, plugins, apps and hooks are still switched off for music jobs, and the prompts tell the model not to use tools.

Music jobs use the model from your Codex config when the pinned CLI supports it. If your config names a newer model the pinned CLI rejects, jobs use the first model in the pinned CLI's own catalog (`codex debug models`) at that model's default reasoning effort. Conversation turns and the first batch of picks after you start or steer the DJ use the same model at low effort, which answers in seconds rather than about half a minute. Two Codex jobs run at once; waiting jobs go in this order: conversation, picks, taste notes, artist notes. `GET /api/v1/capabilities` reports Codex, YouTube discovery and YouTube playback separately. A later login expiry or usage limit may still fail a job.

Feedback is saved immediately to the CSVs. When Codex is ready, a coalesced synthesis job updates `musical_taste.md`; `GET /api/v1/taste` reports its status. `POST /api/v1/dj/recommendations` starts a source-bound recommendation job and returns a `jobId` to poll at `GET /api/v1/jobs/:id`. `DELETE /api/v1/jobs/:id` cancels work. Local ranking uses indexed catalog candidates. For YouTube, Codex names tracks by artist and title, without web search. The server then searches YouTube with yt-dlp, scores the results and keeps only tracks whose audio stream opens. Scoring prefers official "Artist - Topic" uploads and the artist's own channel, and rejects other songs, live versions, covers and full albums. A quick batch keeps 3 tracks, a refill 5. Songs heard recently, in this session or the last 60 plays, are not repeated. A dislike saved while the DJ is choosing removes that track from the batch rather than failing it. Without Codex access the endpoint reports the existing-login problem; it does not return fabricated picks. Known ID3 artist identities can generate cached information through `GET /api/v1/artists/:key/info` and `POST /api/v1/artists/:key/info/refresh`. Unknown artist identities do not trigger generation.
